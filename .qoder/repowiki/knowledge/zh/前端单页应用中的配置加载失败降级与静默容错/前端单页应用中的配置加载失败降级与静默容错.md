## 1. 采用的错误处理策略

该仓库是一个基于 Vite + React 的纯前端单页应用，没有后端服务、中间件或全局异常捕获框架。错误处理集中在**配置文件远程拉取失败时的降级（fallback）机制**上，采用“静默失败 + 内置兜底数据 + 用户可见提示”的模式。

- **无全局 `try/catch` 包裹**：`src/main.jsx` 直接渲染 `<App />`，未使用 `window.onerror`、`unhandledrejection` 等全局监听。
- **无自定义 Error 类型**：代码中仅使用原生 `Error`（见 `pity.js` 第 67 行 `throw new Error(\`HTTP ${res.status}\`)`），未定义业务错误类。
- **无 panic/recover 等价物**：React 组件不使用 `componentDidCatch` 或 `errorBoundary`，错误不会向上冒泡到边界组件。

## 2. 关键文件与位置

| 文件 | 职责 |
|---|---|
| `src/lib/pity.js` | 核心错误处理入口：`loadProfiles()` 用 `try/catch` 包裹 `fetch`，失败时返回 `{ profiles: FALLBACK_PROFILES, failed: true }` |
| `public/config.properties` | 外部配置文件；注释说明了格式与解析规则，是错误处理的“契约”来源 |
| `src/App.jsx` | 消费 `loadProfiles` 的结果，根据 `failed` 标志显示 `.config-warning` 提示 |
| `src/components/MeasuringCup.jsx`、`UserSwitch.jsx` | 纯展示组件，不产生错误 |

## 3. 架构与约定

### 3.1 降级数据模型
`pity.js` 定义了与 `config.properties` 结构一致的内置兜底对象：
```js
export const FALLBACK_PROFILES = {
  userA: { name: 'userA', fates: 6, primogems: 400 },
  userB: { name: 'userB', primogems: 0 },
};
```
注释明确说明“与 config.properties 保持一致即可”，即兜底数据必须与外部配置键名、字段语义对齐，保证 UI 层无需区分数据来源。

### 3.2 解析器的健壮性
`parseProfiles(text)` 对每一行执行以下过滤，避免脏数据导致崩溃：
- 跳过空行、以 `#` 开头的注释行、以 `!` 开头的行（兼容 properties 风格）。
- 通过正则 `/^(userA|userB)\.(fates|primogems|name)$/` 白名单校验键名，未知键直接忽略。
- 数值字段使用 `Number(value)` 并检查 `Number.isNaN(num) && num >= 0`，非法值被丢弃。
- 最终始终返回包含 `userA`、`userB` 两个用户的完整对象，即使输入为空也安全。

### 3.3 网络请求的错误传播
`loadProfiles()` 的调用链：
1. `fetch(config.properties)` 失败（网络错误、404、跨域等）→ 进入 `catch` → 返回 `{ profiles: FALLBACK_PROFILES, failed: true }`。
2. `res.ok === false` 时主动 `throw new Error(...)`，同样落入 `catch` 分支。
3. 成功时返回 `{ profiles: parseProfiles(...), failed: false }`。

因此上层组件只需判断 `failed` 布尔值，无需处理 Promise reject。

### 3.4 UI 层的错误呈现
`App.jsx` 在 `useEffect` 中调用 `loadProfiles()`，将 `failed` 写入 `configFailed` 状态。当 `configFailed` 为真时，在 `<header>` 内渲染：
```jsx
<p className="config-warning">配置文件读取失败，当前使用内置兜底数据</p>
```
这是一种**非阻断式**提示：页面仍正常渲染保底进度可视化，只是告知用户数据来自本地默认值。

## 4. 约定与约束

- **所有可失败的 I/O 操作必须提供兜底返回值**：`loadProfiles` 是唯一可能失败的函数，它保证永远 resolve 一个包含 `profiles` 的对象，从不 reject。
- **解析器必须容忍任意格式的输入**：`parseProfiles` 对每行独立处理，遇到非法行直接 `continue`，不会中断整个解析过程。
- **UI 不得因配置缺失而崩溃**：`App.jsx` 在 `profiles` 为 `null` 时显示“正在读取配置…”占位，确保首屏始终可渲染。
- **错误信息对用户友好**：仅在必要时向用户暴露中文提示（“配置文件读取失败，当前使用内置兜底数据”），不暴露 HTTP 状态码或堆栈。
- **常量集中管理**：`PITY_COST`、`FATE_COST`、`BOOST_THRESHOLD` 等计算常量集中在 `pity.js` 顶部导出，避免魔法数字散落各处。

## 5. 未覆盖的场景

- 组件内部的状态更新错误（如 `calcPercent` 传入负数）未被显式防御，但 `parseProfiles` 已过滤负值，且 `calcPercent` 本身对任意数字均能返回数值。
- 未实现 React Error Boundary，深层子组件抛出的同步异常不会被捕获。
- 无日志记录（console 输出也未用于错误上报）。

总体而言，该仓库的错误处理遵循**“最小化错误面 + 优雅降级”**的前端实践：把风险收敛在单一数据源加载处，通过兜底数据和用户可见提示保证应用始终可用。
